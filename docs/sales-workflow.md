# Продажи и роли: этап 2

Что сделано в форке `marmelab/atomic-crm` (база: `832b07a89be2d9265a66bbf879fed0299c14ebfb`) по этапу «Продажи и роли»
из технического задания. Остальные этапы (сайт и Авито, цех, сообщения, запуск) не затронуты.

## Как воспроизвести

Нужны Node из `.nvmrc` (проверено на 22 и 24) и Docker.

```bash
npm install
npx supabase start
npx supabase db reset --local          # применяет все миграции, включая новую
npm run seed:sales-demo                # аккаунты и заявки для проверки, только на пустой БД
npm run test:sales-api                 # 26 интеграционных тестов через настоящий PostgREST
npm run dev                            # http://localhost:5173
```

Команды выполняются по одной: они одинаково работают в PowerShell, cmd и bash, `make` не нужен
(цели `make seed-sales-demo` и `make test-sales-api` — те же npm-скрипты). Сидер и тесты меняют данные:
после тестов снова выполните `db reset`, прежде чем запускать сидер. Нужны запущенные Docker и `npx supabase start`.

Аккаунты сидера (пароль у всех `Passw0rd!Passw0rd!`):

| Почта | Роли |
| --- | --- |
| `head@crm.test` | администратор, менеджер, руководитель продаж |
| `anna@crm.test`, `boris@crm.test` | менеджер |
| `shop@crm.test` | сотрудник цеха: данных продаж не видит |
| `nobody@crm.test` | роли нет: данных нет |

Проверки кода: `npm run typecheck`, `npm run lint`, `npm run test:unit:app`, `npm run build`.

## Что в базе

Файл миграции: `supabase/migrations/20261120190000_sales_roles_and_deal_commands.sql`, источник правды: `supabase/schemas/`.
Миграция собрана из деклараций скриптом, потому что `supabase db diff` в этой среде не смог скачать пакеты из npm
(прокси). Проверено на базе с уже существующими сделками: суммы сохранены, выигранные сделки помечены историческими,
всем действующим сотрудникам выдана роль менеджера, администраторам ещё и руководителя продаж.

- `staff_roles`: рабочие роли (`manager`, `sales_head`, `production_head`, `workshop`, `fulfillment`). Без роли нет данных продаж.
  Первый зарегистрированный аккаунт получает `manager` и `sales_head`.
- `deals`: `source`, `received_at`, `first_response_due_at`, `first_responded_at`, `version`, `lost_reason`, `is_historical`,
  проверка кодов стадий. `tasks.deal_id`. `business_settings`: часовой пояс, график и срок первого ответа (по умолчанию
  Europe/Moscow, пн–пт 09:00–18:00, 30 минут). `deal_stage_history`: кто, когда, что и почему менял.
- Команды (SQL RPC, одна транзакция каждая): `claim_deal`, `transition_deal`, `assign_deal`, `create_manual_deal`,
  `set_staff_roles`. Принимают ожидаемую версию и ключ запроса: повтор с тем же ключом возвращает тот же результат.
- Ошибки команд приходят кодом `PT<http>` и текстом: `deal_already_assigned` (409), `deal_version_conflict` (409),
  `claim_required`, `won_requires_handoff`, `reason_required`, `not_your_deal` и так далее (422/403).
- Прямые запросы к Data API: триггер `00_deals_guard` запрещает менять стадию, порядок, владельца и системные поля, а
  также создавать сделки, кроме импорта исторических сделок руководителем продаж (`is_historical = true`).
- RLS по ролям: менеджер видит общую очередь и свои сделки, руководитель продаж все. Клиенты, компании, заметки, метки и
  задачи доступны только ролям продаж. Удалять сделки, клиентов и компании может только руководитель продаж.
- Функция Edge `mcp` отключена в `supabase/config.toml`.

## Что в интерфейсе

- Левое меню по ролям, верхняя панель с поиском и пользователем. После входа менеджер попадает на доску продаж.
- Доска: девять колонок с кодами стадий из ТЗ (`opportunity`, `to-contact`, `contacted`, `in-work`, `proposal-sent`,
  `in-negociation`, `won`, `lost`, `delayed`), постраничная загрузка по колонкам с «Показать ещё» и точным счётчиком,
  счётчик очереди без ответственного, сортировка новых заявок по просрочке ответа. Перетаскивание и кнопка «Переместить»
  вызывают одни и те же команды; при конфликте доска обновляется и показывается причина.
- Зона «К передаче в производство» перед «Выиграна» пока только объясняет, что форма передачи появится на этапе «Цех».
- «Новая заявка»: поиск существующего клиента или создание нового (без вымышленного телефона), источник, фактическое
  время обращения, «взять себе» или оставить в общей очереди.
- Карточка сделки: источник, время поступления и срок ответа в часовом поясе компании, ответственный, история.
- «Задачи»: «Мои», «Сегодня», «Просроченные», «Завершённые».
- Пользователи: администратор отмечает рабочие роли. Русский каталог `ru` по умолчанию, суммы в рублях.

## Известные ограничения

- Роли подгружаются при входе: изменение ролей действует после следующего входа.
- Название и стадии в настройках можно менять только по названиям, коды зафиксированы.
- Клиенты и компании видны всем ролям продаж целиком; доступ по связанным сделкам запланирован вместе с перепиской.
- Вложения заметок всё ещё в публичном бакете `attachments`: перевод на приватную выдачу нужен до загрузки реальных данных.
- Старые e2e-тесты Playwright (`e2e/`) написаны под прежний английский интерфейс и вкладки и не обновлялись.
- Тесты `getContactAvatar` обращаются к Gravatar и не проходят без доступа в интернет (так было и до изменений).
