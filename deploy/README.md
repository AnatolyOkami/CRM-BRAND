# Развёртывание на VPS (Beget): CRM и собственный Supabase

Всё работает на одном сервере: приложение, база, вход, файлы и функции Supabase. Данные остаются у вас.
Снаружи виден только веб-сервер Caddy по HTTPS; Supabase и база слушают `127.0.0.1`.

```
браузер ──HTTPS──▶ Caddy ──▶ файлы приложения         (crm.example.ru)
                     └─────▶ шлюз Supabase 127.0.0.1:8000 (api.example.ru)
                                 ├─ база PostgreSQL, вход, файлы, Edge-функции
```

## Что нужно

- VPS с Ubuntu 22.04 или 24.04, не меньше 2 ядер и 4 ГБ памяти (Supabase тяжёлый; сборку приложения на 2 ГБ
  выполняйте с файлом подкачки), диск от 40 ГБ. Доступ по SSH под root.
- Два домена или поддомена, A-записи на IP сервера: `crm.example.ru` (приложение) и `api.example.ru` (Supabase).
  Без них Caddy не получит сертификаты.
- Репозиторий `AnatolyOkami/CRM-BRAND`. Если он приватный, на сервере нужен доступ: SSH deploy key с правом чтения
  (`ssh-keygen -t ed25519`, публичную часть добавить в Settings → Deploy keys) и адрес `git@github.com:AnatolyOkami/CRM-BRAND.git`.

## Установка

Команды выполняются на сервере по одной.

```bash
git clone --branch main https://github.com/AnatolyOkami/CRM-BRAND.git /opt/crm
```
```bash
sudo /opt/crm/deploy/server-setup.sh crm.example.ru api.example.ru
```

Скрипт ставит Docker, Node 22, включает файрвол (открыты SSH, 80 и 443), скачивает файлы Supabase нужной версии
(она зафиксирована в `deploy/versions.env`), создаёт `/opt/supabase/.env` со свежими секретами и запускает Supabase.
Первый запуск скачивает образы, это несколько минут.

```bash
cd /opt/crm && deploy/update.sh
```

`update.sh` собирает приложение, кладёт Edge-функции, накатывает миграции и запускает Caddy. Откройте
`https://crm.example.ru` и зарегистрируйте первого пользователя: он становится администратором и получает роли
«менеджер» и «руководитель продаж». Остальных сотрудников приглашает администратор в разделе «Пользователи», роли
выдаются в карточке пользователя.

Секреты лежат в `/opt/supabase/.env`. Пароль Studio (`https://api.example.ru`, логин `admin`) — `DASHBOARD_PASSWORD`.
Сохраните копию этого файла вне сервера: без него базу не поднять.

## Почта

Приглашения сотрудникам и сброс пароля уходят письмами. В `/opt/supabase/.env` заполните `SMTP_HOST`, `SMTP_PORT`,
`SMTP_USER`, `SMTP_PASS`, `SMTP_ADMIN_EMAIL`, `SMTP_SENDER_NAME` (для почты Beget: `smtp.beget.com`, порт 465) и примените:

```bash
cd /opt/supabase && docker compose up -d auth
```

## Работа с терминала сервера

Ежедневный цикл изменений:

1. Правки делайте в отдельной копии, не в рабочей папке сервера: `git clone https://github.com/AnatolyOkami/CRM-BRAND.git ~/crm-dev`.
2. Проверьте (`npm ci`, `npm run lint`, `npm run typecheck`, `npm run test:unit:app`), закоммитьте, отправьте в ветку и влейте в `main` через pull request.
3. Обновите сервер:

```bash
cd /opt/crm && git pull && deploy/update.sh
```

Если миграция не применилась, `update.sh` останавливается, а файл миграции откатывается целиком (повтор безопасен).
Claude Code в терминале сервера ставится так: `npm install -g @anthropic-ai/claude-code`, затем `claude` в папке `~/crm-dev`.

## Резервные копии: ежедневно в GitHub

Раз в сутки сервер собирает базу и загруженные файлы, **шифрует** их и отправляет в **отдельный приватный**
репозиторий. В репозиторий с кодом данные не попадают никогда. Копия читается только приватным ключом, который
хранится у вас; сервер умеет лишь шифровать, поэтому злоумышленник, получивший сервер или GitHub, прочитать копии не может.
В репозитории остаётся один коммит с копиями за последние 14 дней: история не растёт, старые данные в ней не копятся.

Настройка один раз:

1. На GitHub создайте **приватный** репозиторий, например `crm-backups`.
2. Ключ шифрования:

```bash
/opt/crm/deploy/make-backup-key.sh
```

   Публичный ключ (`age1...`) впишите в `/opt/crm/deploy/web.env` как `BACKUP_AGE_RECIPIENT`, адрес репозитория — как
   `BACKUP_REPO` (`git@github.com:ВАШ-АККАУНТ/crm-backups.git`). **Приватный ключ скопируйте в менеджер паролей и удалите с сервера**
   (команды выведет скрипт). Потеряете его — копии не открыть никому.
3. Ключ доступа к GitHub и расписание:

```bash
sudo /opt/crm/deploy/install-backup.sh
```

   Скрипт выведет SSH-ключ: добавьте его в `crm-backups` → Settings → Deploy keys → «Allow write access».
4. Проверка: `sudo /opt/crm/deploy/backup.sh`. В репозитории должен появиться `daily/crm-ГГГГ-ММ-ДД.tar.age`.
   Копии также лежат на сервере в `/opt/crm-backups/local`, журнал — `/var/log/crm-backup.log`, время последней
   удачной копии — `/opt/crm-backups/last-success`.

**Восстановление** (на новом сервере после установки и `update.sh`, когда таблицы пусты):

```bash
git clone git@github.com:ВАШ-АККАУНТ/crm-backups.git /tmp/crm-backups
```
```bash
sudo /opt/crm/deploy/restore.sh /путь/к/приватному.key /tmp/crm-backups/daily/crm-ГГГГ-ММ-ДД.tar.age
```

Если копия разрезана на части (`.part-aa`, `.part-ab`), передайте все части списком. Скрипт спросит подтверждение:
он заменяет данные CRM. Пароли пользователей хранятся в базе и восстановятся, но все открытые сессии сбросятся и
сотрудникам придётся войти заново (у нового сервера свои ключи Supabase, это нормально). Файл `/opt/supabase/.env`
в копию не входит: держите его копию вместе с приватным ключом. **Раз в квартал проверяйте восстановление на тестовом сервере.**

Важно:

- Данные клиентов относятся к персональным. GitHub находится за пределами РФ: шифрование закрывает риск утечки, но
  вопрос соответствия 152-ФЗ о хранении за рубежом решите с юристом. Надёжная схема: копия в GitHub **плюс** снимок
  диска или хранилище в России (у Beget есть резервное копирование VPS).
- Одной копии в GitHub недостаточно как единственной: держите ещё снимок сервера у провайдера.

## Что где лежит

| Путь | Что |
| --- | --- |
| `/opt/crm` | код CRM, `deploy/web.env` (настройки), `dist/` (собранное приложение) |
| `/opt/supabase` | Supabase: `.env` (секреты), `volumes/db` (база), `volumes/storage` (файлы), `volumes/functions` |
| `/opt/crm-backups` | копии на сервере |

## Что не проверялось

Скрипты проверены на локальном Supabase и на синтаксис; на реальном сервере Beget установка ещё не запускалась.
Проверены отдельно: накат миграций (включая откат при ошибке), копия и восстановление базы и файлов с входом после
восстановления, генерация `.env` на официальном примере, разбор compose с нашим override.
При первом запуске внимательно смотрите вывод `server-setup.sh` и `update.sh`. Особенно проверьте: получение
сертификатов Caddy, регистрацию первого пользователя, приглашение сотрудника (нужна почта) и загрузку файла в форме передачи.
